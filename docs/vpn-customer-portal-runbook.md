# Veltrix: кабинет, закрытая проверка и откат

## Границы выпуска

Кабинет `/cabinet/`, бот и админка используют одних клиентов, подписки и профили.
Авторизация клиента отделена от администраторской. Переименование меняет только
отображаемое имя: UUID, `public_name`, сохранённая VPN-ссылка и настройки ноды не
перегенерируются. Оплаты, выдуманные тарифы и фиктивная статистика не добавляются.

Кабинет развёрнут, но вход и публичный доступ пока выключены. Следующий этап —
только закрытый пилот с явно подтверждённым Telegram ID. Нельзя назначать существующий
`test1` по имени или первому посетителю бота. Владелец уже подтверждён одноразовым сообщением; его ID
хранится только в приватных операционных данных, не в репозитории.

## Публичные значения для Telegram

```text
Bot: @veltrix_vpn_official_bot
Website origin: https://veltrix.qzz.io
OIDC callback: https://veltrix.qzz.io/api/vpn-portal/auth/telegram/callback
Mini App URL: https://veltrix.qzz.io/cabinet/
```

В BotFather открыть существующего бота → Login Widget и зарегистрировать разрешённые
URL сайта и callback. Client ID / Client Secret ввести непосредственно в закрытый
серверный `.env`, без отправки в чат, скриншоты, Git или историю команд.
На момент подготовки пользователь ещё не выполнил эту настройку: вход через обычный
браузер не может считаться проверенным. Вход Mini App использует существующий bot token
и отдельно подписанный `initData`, а не OIDC Client Secret.

Официальные описания: [Telegram Login](https://core.telegram.org/bots/telegram-login),
[проверка Mini App initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

## Настройки закрытого запуска

Публичные параметры первоначального выключенного выпуска:

```dotenv
VPN_PORTAL_ENABLED=false
VPN_PORTAL_PUBLIC_ORIGIN=https://veltrix.qzz.io
VPN_PORTAL_PUBLIC_ACCESS=false
VPN_PORTAL_ALLOW_LOCAL_HTTP=false
```

`VPN_PORTAL_ALLOWED_TELEGRAM_IDS` заполняется только подтверждённым ID в приватном
окружении. `VPN_PORTAL_OIDC_CLIENT_ID` и `VPN_PORTAL_OIDC_CLIENT_SECRET` не заполнять
фиктивными значениями. Сохранить все существующие переменные и права `.env` 0600.
Для закрытого пилота включить `VPN_PORTAL_ENABLED=true`, оставив публичный доступ false.
Кнопка кабинета появится только в приватном чате разрешённого участника при наличии
необходимой конфигурации. Остальным остаются команды бота.

## Перед изменением продакшена

1. Зафиксировать точную исходную и целевую ревизии, проверить рабочие изменения.
   Не удалять `gandi-probes/`, egg-info, пользовательские файлы или изменённый
   `frontend/tsconfig.tsbuildinfo`. Не выполнять `reset --hard` и массовый `clean`.
2. Проверить активные attack/worker/maintenance/zone-scan задания. Не прерывать
   захват доменов или обслуживание ноды. Обычные постоянно работающие discovery
   задания учитывать отдельно; не выдавать их наличие за «сервер полностью простаивает».
3. Проверить фактический unit, Nginx include-контексты, allowlist воркеров, свободное
   место и публичный `/api/health`.
4. Создать новую серверную копию полной БД (`pg_dump` custom, закрытые права),
   `.env`, unit, Nginx, прежней frontend-сборки и изменённого build cache.
   Проверить TOC дампа и архивы. Не передавать БД и ключи на другой компьютер.
5. Записать путь копии и исходную ревизию. Старые частичные/устаревшие копии не
   подменяют свежую. Хеши старой VPN-идентичности позволяют проверить отсутствие
   изменений, не выводя URI/UUID в журналы.

## Порядок выпуска

Свежая копия для этого выпуска: `/opt/backups/veltrix-cabinet-20260921-003811`.
Дамп 1 133 002 179 байт, TOC обязательных таблиц и config/frontend архивы проверены.
Это сохранённая копия для восстановления, не удалённая репетиционная БД.
Тестовый Nginx 1.18 прошёл изолированную проверку 200/400/413/429/502, cookie,
заголовков и секретов в журналах; тестовый экземпляр удалён. Продакшен обновлён
до `46caa10`: перезапущен только control, Nginx проверен и перезагружен без остановки.
VPN-ноды, транспорт и фактический systemd unit не менялись. Вход в кабинет выключен.

Пункты 1–6 ниже выполнены. Пункт 7 — следующая стадия с настоящим Telegram-клиентом;
на момент этого выпуска она не выполнена. Автоматический откат подготовлен и проверен
на уровне сценария; принудительный откат исправного продакшена не выполнялся.

1. Закончить тесты и обе независимые проверки защиты журналов. Проверить Nginx-сниппеты на
   отдельном временном loopback-экземпляре с вымышленными данными: 200/400/413/429/502,
   cookie, no-store/no-referrer и отсутствие секретов во всех его журналах.
2. HTTP-сниппет подключается внутри `http {}`, до server-блоков. Сниппет locations —
   только в основном HTTPS server. Безопасные access/error настройки нужны также
   HTTP redirect и прямому worker server: туда нельзя добавлять proxy кабинета.
   Существующий worker allowlist сохраняется. Сначала `nginx -t`, затем reload.
3. Установить проверенную PyJWT отдельно без обновления всего Python или обхода
   требования проекта к стабильной версии интерпретатора. Проверить импорт.
4. Доставить только проверенный commit, собрать frontend, оставить кабинет выключенным.
   Аддитивная миграция выполняется при старте control. Перезапускать только
   `domain-drop-control.service`, не VPN-ноды и не PostgreSQL.
5. Проверить локальный и публичный health, админский вход, существующих клиентов и
   ссылки, кабинет и его выключенную конфигурацию. Проверить новую версию схемы и
   сохранность прежней VPN-идентичности, не печатая ключи.
6. Проверить HTTPS с валидацией сертификата и DNS через существующий VPN-профиль.
   Смена видимой подписи не должна менять credential/host/port/transport.
7. Только после этих проверок разрешить подтверждённый закрытый пилот. Настоящие
   Telegram browser/iPhone проверки выполнить с владельцем, когда он доступен.
   До этого не утверждать «вход с iPhone проверен» или «готово к публичным продажам».

## Проверка пилотом после входа

- Открыть кабинет из приватного чата бота; профиль и подписка совпадают с админкой.
- Перезагрузить `/cabinet/`, проверить узкий экран, выбор/копирование полной ссылки.
- Переименовать профиль; старая VPN-идентичность сохранена, новая подпись появилась
  в кабинете, боте и админке. Проверить подключение Happ.
- В обычном браузере пройти Telegram callback; отдельно отменить вход.
- Проверить выход, просроченную сессию, повторный запуск Mini App и сосуществование
  админской/клиентской сессий. Другой клиент не должен видеть чужие профили.
- Публичное включение — отдельное решение; платёжная интеграция остаётся выключенной.

## Обратимый откат

При проблеме сначала выключить `VPN_PORTAL_ENABLED`, оставив `PUBLIC_ACCESS=false`.
Перезапустить только control: новые входы и кнопка кабинета будут недоступны.
При необходимости отозвать именно клиентские portal-сессии, не админские и не VPN-ключи.

Возврат приложения: развернуть сохранённую предыдущую ревизию и frontend-сборку,
восстановить только изменённые настройки из свежего config backup, проверить Nginx
и control health. Аддитивные таблицы/колонку оставить — совместимость со старым ORM
проверена. Не откатывать всю рабочую БД поверх новых подписок и изменений клиентов.
Не удалять резервную копию до подтверждённого завершения проверки.

## Что не входит в этот выпуск

Платежи, публичные цены/маркетинговые лимиты, реальный сбор статистики трафика,
новая TLS/REALITY конфигурация нод и обновление серверного Python требуют отдельных
проверяемых этапов. Текущий работающий plain VLESS-профиль не меняется этим выпуском.
