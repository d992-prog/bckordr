# Veltrix VPN: fleet-мониторинг и релизная эксплуатация

**Дата:** 24 сентября 2026 года  
**Статус:** дизайн согласован владельцем; оплата и публичное включение не входят в этот этап.

## 1. Цель

Сделать эксплуатацию Veltrix пригодной для широкой аудитории без ручной работы с
каждой VPN-нодой. Система должна сама контролировать парк нод, резервные копии,
очереди и публичные поверхности, показывать точные причины блокировки релиза и
отправлять владельцу одно понятное Telegram-уведомление на проблему и одно — на
восстановление.

Публичный trial остаётся выключенным. Этот этап создаёт проверяемые релизные
ворота, но не включает их автоматически и не добавляет оплату.

## 2. Подтверждённое исходное состояние

- В продакшене зарегистрирован один `ready` REALITY endpoint на одном VPN-worker.
- Для endpoint не задан `max_active_profiles`, а сохранённая проверка здоровья
  старше допустимых 300 секунд. Поэтому endpoint не подходит для публичной
  автоматической выдачи.
- На управляющем сервере нет отдельного Veltrix-watchdog и расписания полной
  резервной копии приложения.
- В проекте уже есть массовые операции `vpn-update-all` и
  `vpn-autoconfig-all`, защищённый one-shot deployer и строгий dispatcher.
- Существующий общий `vpn_check` использует старый SSH-путь без проверки
  `known_hosts`; он не считается доказательством релизной готовности.

## 3. Рассмотренные варианты

### Внешний uptime-сервис

Быстро проверяет HTTP, но не видит PostgreSQL, очередь, ёмкость, резервные копии и
фактическое состояние нод. Может быть добавлен позже как независимый внешний
датчик, но не заменяет релизный контур.

### Prometheus, Grafana и Alertmanager

Дают богатые графики, но добавляют три сервиса, их хранение, обновление и
собственный мониторинг. Для текущего масштаба это лишняя эксплуатационная
поверхность.

### Встроенный readiness-сервис и маленькие systemd-задачи — выбранный вариант

Используются текущие FastAPI/PostgreSQL/Telegram-механизмы, стандартный systemd и
один независимый watchdog-процесс. Новых инфраструктурных зависимостей нет.
Админка, публичный gate и watchdog используют один вычислитель готовности.

## 4. Fleet-принцип

Нода не получает индивидуальную реализацию. Новый VPS проходит один одинаковый
конвейер:

1. создание worker и подтверждение его Ed25519 host key;
2. one-shot установка проверенного node bundle;
3. создание REALITY endpoint;
4. один внешний тест HTTPS/DNS через одноразовый профиль;
5. задание ёмкости и включение в общий парк.

После этого обновление запускается существующей массовой операцией для всех
допустимых нод. Проверки здоровья, readiness и алерты также обходят весь парк.
Добавление третьей и последующих нод не требует нового кода или отдельного
скрипта.

Внешняя проверка нужна только при первом вводе endpoint и после изменения его
идентичности: host, port, inbound, REALITY public key, server name или short ID.
Обычное обновление node bundle или 3x-UI не требует повторного ручного онбординга,
если идентичность endpoint сохранилась.

## 5. Компоненты

### 5.1. Единый вычислитель релизной готовности

Чистый backend-сервис возвращает список проверок с кодом, состоянием
`pass/warn/fail`, безопасным русским описанием и временем наблюдения. Он проверяет:

- control service/API и PostgreSQL;
- публичный health и кабинет;
- свежую полностью проверенную резервную копию;
- свободное место;
- отсутствие застрявших VPN-операций и maintenance-задач;
- корректный семидневный тариф на одно устройство;
- минимум два `ready` REALITY endpoint на разных активных worker;
- положительную ёмкость каждого публичного endpoint;
- свежую строгую проверку здоровья каждого endpoint;
- сохранённое внешнее подтверждение endpoint;
- отсутствие исчерпанной общей ёмкости;
- выключенную оплату.

API возвращает только агрегаты и безопасные идентификаторы. SSH-адреса, токены,
UUID и VPN URI не включаются.

### 5.2. Строгая fleet-проверка здоровья

Для node bundle добавляется отдельная read-only health-команда. Она запускается
через существующий strict SSH transport с закреплённым Ed25519 host key и
возвращает ограниченный JSON без секретов. Проверяются:

- доступность node runner;
- состояние 3x-UI/Xray;
- наличие ожидаемого inbound;
- совпадение host/port/protocol/transport/REALITY identity;
- слушающий публичный порт;
- неизменность существующих client identities.

Успех обновляет существующие `vpn_last_checked_at`, `vpn_runtime_status`,
`VpnEndpoint.verified_at` и очищает безопасный error code. Ошибка не меняет VPN,
не запускает restart и делает endpoint непригодным для новых публичных назначений.

Control runtime запускает ограниченную fleet-проверку по расписанию. Одновременно
проверяется не более одной ноды; занятые мутацией или обслуживанием ноды
пропускаются до следующего цикла. Старый небезопасный SSH `vpn_check` не
используется автоматикой и не влияет на публичный gate.

### 5.3. Внешнее подтверждение нового endpoint

В endpoint хранится `external_verified_at` и отпечаток публичной конфигурации.
Администратор может отметить внешний тест успешным только после одноразового
подключения тестового профиля. Действие аудируется и не содержит URI/UUID.

Если меняется публичная идентичность endpoint, подтверждение автоматически
сбрасывается. Обновление с неизменной идентичностью его сохраняет.

### 5.4. Watchdog и Telegram-алерты

Отдельный systemd timer каждые пять минут запускает короткую CLI-команду из
backend-пакета. Она работает независимо от web-процесса, поэтому может сообщить
о падении control service. Проверка использует тот же readiness-сервис, а при
недоступной БД всё равно проверяет systemd, HTTP, диск и backup marker.

Состояние дедупликации хранится в root-private JSON-файле. Для одного набора
причин отправляется одно сообщение; повторов нет до изменения причин. После
устранения отправляется одно сообщение «восстановлено». Telegram-токен и user ID
никогда не выводятся в argv, журнал или ответ API.

### 5.5. Автоматическая резервная копия

Ежедневный systemd timer создаёт новую директорию `.partial`, выполняет custom
`pg_dump`, полное потоковое чтение через `pg_restore`, SHA-256, копирование `.env`,
фактического unit, nginx и текущего frontend `dist`. Только после всех проверок
директория атомарно становится успешной и обновляет безопасный marker.

Хранятся последние семь успешных копий. Старые успешные копии удаляются только
после завершения новой. Незавершённые копии не считаются успешными и не
подменяют marker. Все каталоги имеют `0700`, файлы с секретами и дамп — `0600`.

### 5.6. Админский экран «Готовность к релизу»

Экран показывает общий статус, время последней проверки и сгруппированные
причины: инфраструктура, ноды, ёмкость, очередь, backup и продуктовые флаги.
Для каждой причины есть короткое действие, ведущее к уже существующей панели
ноды, capacity или maintenance.

Кнопка «Зафиксировать готовность» доступна только при всех hard checks `pass`.
Она записывает существующий `vpn_public_release_ready_v1`, но не меняет `.env` и
не включает публичный trial. Включение флага остаётся отдельным выпуском с
резервной копией и наблюдением.

## 6. Данные и совместимость

Аддитивно добавляются только поля внешней проверки endpoint и, при необходимости,
безопасный отпечаток его публичной конфигурации. История клиентов, UUID, URI,
подписки и текущие назначения не меняются.

Readiness-снимок не получает отдельную таблицу: он вычисляется из существующих
данных. Последнее состояние watchdog хранится на диске, события нод продолжают
использовать `vpn_node_events`, административное подтверждение — существующий
аудит.

Предыдущая версия приложения должна продолжать работать с добавленными колонками.

## 7. Ошибки и безопасное поведение

- Любая неизвестная или просроченная проверка блокирует только новые публичные
  trial, но не отзывает существующие подключения.
- Watchdog никогда не перезапускает VPN-ноду автоматически.
- Массовое обновление использует существующие блокировки active attack,
  maintenance и VPN-control operations.
- Ошибка одной ноды не останавливает проверку остальных.
- Недоступный Telegram не меняет readiness; уведомление повторяется с ограниченной
  задержкой, без потока сообщений.
- Ошибка backup не удаляет последнюю успешную копию.
- Ни один автоматический процесс не включает оплату или публичный trial.

## 8. Проверки

- Unit-тесты вычислителя всех `pass/warn/fail` причин.
- PostgreSQL-тесты двух нод, stale health, capacity и конкурентного изменения
  release marker.
- Контрактные тесты strict health request/receipt и отказа при несовпадении
  endpoint identity.
- Тесты fleet-планировщика: одна нода одновременно, skip busy, продолжение после
  ошибки.
- Тесты дедупликации alert/recovery и маскирования секретов.
- Тест backup на временной PostgreSQL: успешный dump/restore, оборванный dump,
  retention и сохранение предыдущей успешной копии.
- API и frontend-тесты экрана readiness.
- Production build, Ruff, полный backend/frontend suite и `git diff --check`.
- Перед продакшеном — закрытая копия реальной БД, backup/restore rehearsal и
  контроль сохранности существующих VPN-идентичностей по хэшам.

## 9. Развёртывание

1. Код и миграции разворачиваются с watchdog, fleet health и backup timers
   выключенными.
2. Проверяется readiness API и админский экран на текущей единственной ноде;
   ожидаемый результат — блокировка по второй ноде, capacity и stale health.
3. Включается ежедневный backup timer, создаётся и полностью проверяется первая
   автоматическая копия.
4. На текущей ноде устанавливается проверенный strict node bundle и включается
   fleet health; существующие UUID/URI и Xray generation не меняются.
5. Настраивается watchdog и проводится тестовый alert/recovery.
6. Второй VPS добавляется тем же one-shot конвейером; отдельной разработки под
   него нет.
7. После внешней проверки обеих нод и задания capacity readiness становится
   зелёным. Публичный trial всё ещё остаётся выключенным до отдельного решения.

## 10. Нецели

- платёжный провайдер, заказы, чеки и возвраты;
- Prometheus/Grafana и долговременное хранилище метрик;
- автоматический restart или update VPN при health-ошибке;
- прозрачная миграция уже импортированного VLESS-профиля между нодами;
- сбор сайтов, DNS-запросов или содержимого трафика;
- индивидуальные скрипты и ручное обновление каждой ноды.

## 11. Критерии готовности блока

- все зарегистрированные VPN-ноды видны одним fleet-снимком;
- массовое обновление остаётся единственным штатным путём обновления парка;
- health каждой ноды обновляется автоматически через strict transport;
- stale/unhealthy/full нода не получает новые публичные профили;
- владелец получает одно alert и одно recovery без дублей;
- ежедневный backup создаётся, полностью читается и контролируется watchdog;
- админка точно объясняет каждый закрытый release gate;
- добавление следующей ноды требует только стандартного онбординга, а не нового
  кода;
- публичный trial и оплата остаются выключенными.
