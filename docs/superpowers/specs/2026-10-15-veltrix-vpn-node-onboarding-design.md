# Единый ввод VPN-ноды в Veltrix

Дата: 2026-10-15.

## Решение

Панель получает один основной сценарий «Настроить VPN-ноду» вместо цепочки
«Установить VPN» → «Автонастроить» → «Создать входящее подключение». Сценарий
использует уже реализованный защищённый стек Veltrix: строгий SSH с закреплённым
Ed25519-ключом, служебный node runner, VLESS/TCP/REALITY на TCP 443, регистрацию
`VpnEndpoint`, проверку здоровья и подтверждение внешнего подключения.

Старые операции остаются только в сворачиваемом разделе «Диагностика» для
аварийного восстановления. Они больше не являются штатным способом добавления
сервера и не могут выдать обычный VLESS-профиль на 8443 как готовую релизную
ноду.

Оплата, цены, публичные тарифы и изменение уже работающих VPN-нод в эту работу
не входят.

## Почему возникла ошибка на `polish-server`

Установка 3x-UI завершилась успешно, но на сервере не появился ни один inbound.
Текущая «Автонастройка» ничего не создаёт: она только ищет уже существующий
inbound. При этом отдельная старая операция создания inbound рассчитана на
устаревшую схему, а успешная установка 3x-UI преждевременно отмечает ноду как
готовую. Поэтому панель показала технические ошибки при фактически незавершённой
настройке.

На `polish-server` подтверждено безопасными проверками:

- 3x-UI запущен, база существует, таблицы inbound пусты;
- TCP 443, 8443 и 2053 свободны;
- защищённый node runner и его root-only конфигурация ещё не установлены;
- endpoint в управляющей базе отсутствует;
- Ed25519 fingerprint, полученный из SSH-рукопожатия и сверенный с публичным
  ключом самого сервера: `SHA256:mhKbdqg44ln3ZCYjiHDCzAHie8TwJZ5Vp5V/GhmoiTc`.

Последняя сверка подтверждает согласованность одного сервера, но не заменяет
независимую проверку fingerprint в консоли хостинга. Поэтому первый запуск на
новой ноде содержит отдельное подтверждение доверия.

## Пользовательский сценарий

Карточка VPN-ноды показывает один следующий шаг:

1. **Проверить сервер.** Панель выполняет только чтение: проверяет SSH,
   архитектуру, root-доступ, системные службы, занятые порты и Ed25519-ключ.
2. **Подтвердить SSH-ключ.** Панель показывает fingerprint и предупреждает, что
   его желательно сверить в консоли хостинга. Администратор либо подтверждает
   совпадение, либо явно выбирает «Доверять этому серверу». Перед записью pin
   backend повторно получает ключ и отказывает при любом изменении.
3. **Настроить VPN-ноду.** Одна фоновая операция проходит все автоматические
   этапы и может безопасно продолжиться после повторного запуска.
4. **Проверить подключение.** Панель выдаёт одноразовый тестовый профиль. После
   реального подключения администратор нажимает «Подключение работает».
5. **VPN-нода готова.** Только после очистки тестового клиента и повторной
   проверки endpoint становится доступен для выдачи пользовательских профилей.

Прогресс выводится человеческими этапами без shell-команд, токенов и сырых
ответов 3x-UI: «Проверяем сервер», «Устанавливаем VPN», «Создаём защищённое
подключение», «Проверяем ноду», «Нужна проверка подключения», «Готово».
Каждая ошибка содержит понятную причину и одно безопасное действие: исправить
настройку, повторить этап либо открыть диагностику.

## Backend и состояния

Новый orchestrator переиспользует существующие сервисы, не дублируя их логику:

- `vpn_node_deployment` — запись pin и установка общего node runner;
- `vpn_reality_endpoint_deployment` — worker-bound installer;
- `vpn_reality_endpoint_installer` — создание и проверка REALITY endpoint;
- `vpn_reality_endpoint_registration` — staged/ready-регистрация;
- существующие health, capacity и external-verification проверки.

Для фоновой работы переиспользуется `WorkerMaintenanceJob` с новой операцией
`vpn_onboard`. Источник текущего состояния — сама инфраструктура: закреплённый
host key, установленный runner, публичный receipt и `VpnEndpoint`. В job пишутся
только безопасный код этапа и безопасный код ошибки; произвольный stdout со
сервера в API и интерфейс не возвращается.

После подтверждения host key весь конвейер работает только через существующий
строгий pinned-SSH transport. Устаревший `execute_worker_ssh_commands()` с
`known_hosts=None` в новом сценарии не используется.

У `WorkerNode` сохраняются подтверждённые публичные поля SSH host key и его
fingerprint. Пароль, приватный ключ SSH, API-токен 3x-UI, UUID тестового клиента,
private key REALITY и полная клиентская ссылка не попадают в job, audit log или
события.

Одноразовый тестовый UUID вычисляется детерминированно через HMAC из серверного
секрета и публичной идентичности endpoint. Поэтому тест можно безопасно
восстановить после перезагрузки страницы без отдельной таблицы и без сохранения
секрета в логах. После подтверждения он удаляется с ноды; endpoint повторно
инспектируется и только затем переводится из `staged` в `ready`.

## Автоматический конвейер

Операция `vpn_onboard` выполняет следующие идемпотентные этапы:

1. блокирует выбранного worker и отказывает для архивной/выключенной ноды,
   активной атаки, параллельного VPN-управления или несовпавшего host key;
2. устанавливает либо проверяет 3x-UI и нормализует только известные владельца и
   права рабочих файлов;
3. до изменения 3x-UI создаёт локальную root-only резервную копию его базы;
4. создаёт отдельный root-only API-токен и node config, не меняя пароль панели;
5. устанавливает проверенный общий node runner и worker-bound endpoint installer;
6. создаёт или подтверждает точный VLESS/TCP/REALITY endpoint на TCP 443;
7. регистрирует его как `staged`, задаёт начальную ёмкость 20 профилей и запускает
   строгую проверку здоровья;
8. переводит карточку в состояние «Нужна проверка подключения».

Каждый этап сначала наблюдает текущее состояние. Точное совпадение считается
успехом, отсутствие создаётся, а частичное совпадение, неизвестный inbound,
занятый TCP 443, сменившийся host key или неоднозначный результат останавливают
конвейер без попытки «починить наугад». Повторный запуск продолжает работу с
первого незавершённого этапа.

Для внешней проверки backend добавляет одноразового клиента, отдаёт профиль
только текущему администратору и ждёт явного подтверждения после реального
подключения. Подтверждение удаляет клиента, доказывает чистое состояние endpoint,
сохраняет digest свидетельства, продвигает endpoint в `ready`, запускает свежий
health check и записывает `external_verified_at`. Если очистка или проверка не
доказана, нода остаётся `staged` и не участвует в выдаче доступов.

## API и интерфейс

Добавляются узкие admin-only методы:

- `POST /control/workers/{id}/vpn-onboarding/preflight` — read-only проверка и
  fingerprint;
- `POST /control/workers/{id}/vpn-onboarding/trust` — повторная сверка и запись
  pin;
- `POST /control/workers/{id}/vpn-onboarding/start` — запуск/продолжение job;
- `GET /control/workers/{id}/vpn-onboarding` — безопасное состояние и следующий
  шаг;
- `POST /control/workers/{id}/vpn-onboarding/test-profile` — временный профиль;
- `POST /control/workers/{id}/vpn-onboarding/confirm` — очистка, promotion и
  внешнее подтверждение.

Секретные ответы получают `Cache-Control: no-store`. Для всех mutating методов
сохраняются существующие admin-аутентификация, аудит, row lock и запрет
параллельных VPN-операций. Повторное нажатие не создаёт второй job, inbound,
endpoint или тестового клиента.

В основной карточке остаётся одна большая кнопка текущего этапа и короткое
описание. Технические значения панели, inbound и legacy-кнопки убираются под
«Диагностику». История показывает только этап, время и понятный итог.
Одна успешная установка 3x-UI больше не может выставить worker состояние
`ready`: готовность означает только `ready` endpoint со свежими health и external
verification.

## Ошибки и восстановление

- До первой мутации любой preflight-запрет ничего не меняет.
- Перед изменением базы 3x-UI создаётся резервная копия с ограниченным сроком
  хранения; неизвестная или неоднозначная конфигурация не перезаписывается.
- Сетевой обрыв после мутации считается неопределённым результатом: следующий
  запуск сначала выполняет inspect, а не повторяет запись.
- Staged endpoint никогда не получает пользовательские профили.
- Ошибка одной новой ноды не меняет ready-endpoint других серверов.
- Откат приложения оставляет ноду staged; существующие профили и готовые ноды
  продолжают работать.

## Проверка и выпуск

До production нужны:

- unit-тесты state machine, повторных запусков, смены host key, конфликтов порта,
  очистки тестового клиента и отсутствия секретов в ответах/логах;
- API-тесты прав администратора, блокировки параллельных операций, no-store и
  идемпотентности;
- integration-тесты со строгим тестовым SSH/3x-UI и PostgreSQL;
- frontend-тесты каждого состояния, обновления страницы и понятных ошибок;
- полный существующий VPN regression suite, Ruff, TypeScript build и lint.

Production-выпуск начинается с резервной копии управляющей базы и базы 3x-UI
`polish-server`. Затем новая схема применяется сначала только к `polish-server`:
fingerprint подтверждается, конвейер создаёт staged endpoint, внешний тест
проходит через выданный временный профиль, после чего проверяются health,
capacity и отсутствие изменений на существующих нодах. Только после этого
единый сценарий становится штатным для следующих серверов.
